## 一、项目目标（一句话）

把 Agent 层从**"自动化全绿"**推进到**"真人与真环境验证过、且改坏了能退回去"**：
先建立可回滚的版本控制，再消掉唯一一个会让用户被骗的功能缺口（提醒重启即丢），
最后把"必须人来做"的验收压成一份照做即可的执行包。

#### 为什么本轮只做"守护"、把"适配层"留给人工（§五点八）

`p4-plan.md` §六 与 §八 把"是否接受 P4-B1 的改动面"明确列为**人工决定**。两条路径：

| 路径 | 改动面 | 风险 |
|------|--------|------|
| **A. 守护 + 显式拒绝**（本轮采用） | 只加 `assert_kernel_bus` 与测试；**不动**任何调用方的契约 | 低 —— 不碰语音管线 |
| B. 加适配层把两个总线统一 | 会动 `core/app.py`、`services/voice_service.py` 等受 G12 保护的路径 | 高 |

只做 A 的理由：**事故的形态不是"契约不统一"，而是"接错了却不报错"。**
D14 那次事故（Agent 层自 P0 起在真实应用里全程静默降级）之所以能藏那么久，
是因为 `AttributeError` 被上层 `except` 吞了。A 恰好堵住这个洞，且零改动面。

> **我自己的测试被真实契约推翻一次**：我按 `handler(**kwargs)` 写断言，
> 跑出来才发现内核总线的 handler 收的是**一个位置参数 `Event` 对象**
> （`core/kernel/events.py:160 handler(event)`）。改成实测契约后 12/12 通过。
> 顺带把 P3 踩过的坑钉住：`emit(t, source="x", value=7)` 里 `source`
> **不进 `data`**（它是 `emit` 的第二个形参）—— 这正是当时事件负载里没有计划来源、
> 测试读 `started["source"]` 直接 `KeyError` 的原因。

### P4-B2 列表参数类型（缺陷 17b）

| 验收条件 | 判定方法 |
|---------|---------|
| 显式拒绝 | `file_search(dirs="Downloads")` → 返回**明确错误**（说明期望数组），**不再**静默回退默认目录 |
| 覆盖四态 | 测试覆盖 `list` / `str` / `None` / 逗号串 四种输入，断言各自的确定行为 |

#### P4-B5 执行实录：一句招呼曾能执行一次删除（§五点七）

**根因**：`RuleRouter._matches_any` 原为朴素子串匹配 `if p in text`，而
`CONFIRM_PHRASES` 含**单字「好」**、`CANCEL_PHRASES` 含**单字「否」**。
待确认项存在时（`has_pending_confirm=True`）真实 `RuleRouter` 实测：

| 用户说 | 修前 | 后果 |
|--------|------|------|
| 「你好呀」 | **`confirm`** | 一句招呼 → 放过待确认的 `file_delete` |
| 「我很好」 | `confirm` | 同上 |
| 「好奇怪」 | `confirm` | 同上 |
| 「好久不见」 | `confirm` | 同上 |
| 「你是否在听」 | `cancel` | 用户只是提问，待确认项却被撤掉 |

`confirm` 是**唯一会直接把用户推进副作用**的路由分支，对应 §5.2 的 R1
「误操作损坏文件」。它比 B5 原本要修的"「算了」听不准"严重得多：
原缺陷是"没反应"，这个缺陷是"**替用户批准了他没批准的操作**"。

**修法（已写进 `_matches_any` docstring 作为契约）：确认从严、取消从宽。**

| 出错方向 | 代价 |
|---------|------|
| 误判成 confirm | **直接放过待确认的删除** |
| 误判成 cancel | 待确认项被撤掉，用户再说一遍（无损） |
| 漏判 confirm | 待确认项挂着，用户再说一遍（无损） |
| 漏判 cancel | 待确认项挂着，用户以为取消了（非破坏性） |

- 严格档（confirm）：剥标点后短语命中，且**剩余字符只能是语气助词或单字应答**
- 宽松档（cancel）：多字短语子串命中（保住「我不要了」这类真实说法）
- **单字短语两档都不做子串匹配**，必须整句成立
- 语气助词表**绝不收「是 / 对 / 行 / 不」**等实义字

> 我自己的第一版修法**被自己的测试推翻一次**：只做"单字整句 + 多字子串"时，
> 「这不太好吧」（一句**反对**）因含子串「好吧」被判成 `confirm`。
> 于是才改成宽严分档；剩余集里允许"别的单字应答"是为了保住「好的，删吧」
> 这种复述式确认（它仍挡得住「这不太好吧」—— 那里的剩余是「这不太」）。
>
> 另：`services/voice_service.py` 加载 ASR 时**不传 params**（`load(asr_engine)`），
> 而 `core/app.py::_load_plugins` 是传的 —— 两条路径不一致，走前者时
> `model_size`/`initial_prompt` 都会静默失效（这也能解释"config 写 medium、
> 回环实际用 small"的旧记录）。**本轮未改**（会动到受 G12 保护的语音路径），
> 已登记待处置。

**⚠️ 真人语音仍未验证**：本节所有数字来自 **TTS 替身**链路。
"真人说「算了」会不会也被听成「散了」"**没有测过**，不可外推 ——
真人那一条在 `docs/agent/manual-acceptance.md`（P4-A3）。

> ⚠️ **顺带暴露一层新问题（未修，如实登记）**：即使拆出计划，**参数类型也常不对**。

> `source: "${s2.paths}"`（`file_move.source` 是 string，而占位符整值解析会保留列表）、
> `targets: ["${s3.paths}"]`（把列表又套了一层）。
> `LLMPlanner._validated_steps` 只校验**工具名**，不校验**参数类型**；
> 于是这类计划会走到执行期才被 `validate_params` 拦下，用户听到的是
> "这个指令我还没完全理解" —— 与 P4-B2 是同一类问题的上游成因。

#### 三、本任务同时抓到的 3 处"探针自己出错"（与 §六 的 7 处同类）

| # | 缺陷 | 后果 | 修法 |
|---|------|------|------|
| 1 | `probe_llm_capability._build_engine` 透传参数时**漏了 `model`** | 探针自称"用 config.yaml 的真实配置"，实际用的是插件默认模型 —— **它没在测它声称测的东西**（实测把 `openai/gpt-oss-120b` 换成了 `llama-3.1-8b-instant`） | 把 `model` 加进透传列表 |

| 3 | `probe_free_llm_matrix` 把 `registry.to_llm_schemas()`（**已包好**的 `{"type":"function","function":{…}}`）直接喂给 `chat_with_tools`（它**会再包一层**） | `function.name` 消失 → **六个免费模型的 ③ 全被判 FAIL**，全是假 FAIL | 新增 `_flatten_schemas()` 统一成扁平格式；修正后同样的模型 **3/3 通过** |

第 3 处还牵出一个**真实存在的接口歧义（未修，登记为 D16）**：

`LLMPlanner._format_tools` 两种都容忍（所以产品当前**没有**因此出错），
但任何新调用方把注册表的 schema 递进去都会得到"工具没有名字"的静默失败。

### P4-B2 执行实录：兜底为什么必须收窄（§五点六）

> 结论先行：**`None`（用户没说）与"用户说了但我不认识"原先共用同一个出口**
> （`_resolve_dirs` 末尾的 `return result or self._default_dirs()`），
> 而这个出口同时被**写操作**用到。收窄成"只有未指定才兜底"之后，
> 认不出的名字一律显式拒绝。完整原始输出见 `docs/agent/evidence/p4/list_param.txt`。

受控沙箱（四个白名单目录；Desktop 有 a/b.txt，Downloads 有 c.txt）：

| 观测点 | 改前 | 改后 |
|--------|------|------|
| `_resolve_dirs("Downloads")` | **4 个目录**（逐字符解析全失败 → 兜底） | 抛 `ParamError`：期望数组 + 可照抄写法 |
| `_resolve_dirs(["Downloads"])` | 1 个目录 | 1 个目录（不变） |
| `_resolve_dirs(["下载"])` | **4 个目录**（中文别名不是白名单根名） | 抛 `ParamError`：不认识这些目录 |
| `file_search(dirs="Downloads", pattern="*.txt")` | 命中 **3 个**（含 Desktop 的） | 拒绝，命中 0 |
| `file_move(dest="不存在的目录")` | **成功**，文件进 Desktop | 拒绝，文件**留在原处** |
| `file_delete(dirs="Downloads", pattern="*.txt")` 预览 | "找到 3 个文件（c.txt、a.txt、b.txt）" | 无预览（参数不合法） |
| 同一份参数的 `execute` | 类型错、一个都不删 | 类型错、一个都不删（**与预览一致**） |

**三处缺陷，按危险度排序**：

1. **`file_move` 的目标目录被静默替换**（本轮新发现，旧记录里没有）
   `_resolve_dirs` 兜底出四目录 → 取 `dirs[0]` = **Desktop** → 文件被挪到桌面**并报成功**。
   安全守卫拦不住它：守卫只拒"白名单外的绝对路径"，而"下载"/"软件归档"这种
   **认不出的相对名字**根本不在白名单校验的语义里（实测 `guard.check` 对它们 `rejected=False`）。
   这是**写操作**上的静默做错事 —— 比"搜多了几个文件"严重一档。
2. **范围静默扩大**：字符串 `dirs` → 四个目录全搜；多出来的路径会经
   `${s1.paths}` 流进 `file_delete` 的待删列表。
3. **预览与执行结论不一致**（"确认范围撒谎"）：`pipeline._tool_preview`
   直接调 `preview(params)`，**绕过 `validate_params`**，于是展示了一个
   永远不会被执行的删除范围。已改为"先校验、再预览"。

**顺带澄清旧记录里的一处担心不成立**：`file_delete(targets=<str>)` 并不会
"把字符串拆成多个待删目标" —— 实测 `_collect_targets({"targets": "C:\\x\\a.txt"})`
返回 `[]`（**整条忽略**）。真实风险是"目标被静默丢掉"，不是"被拆开"。

**契约变更的透明记录**：两处旧用例把缺陷钉成了期望行为，本次改为钉住新契约
（断言**更严**，不是放宽）——
`test_resolve_dirs_all_invalid_falls_back` → `..._is_rejected`、
`test_move_unknown_dest_dir_falls_back_default` → `..._is_rejected`（并新增"拒绝时绝不动文件"）。
