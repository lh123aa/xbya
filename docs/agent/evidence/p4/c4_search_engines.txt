  一个必须点明的结构性问题（不是本次的 bug，但是下一次的 bug）：
  解析器第 1 层只认必应标记 —— `_ENGINE_RESULT_BLOCK_RE`（browser_tools.py:190）
  形如 `<li class="b_algo"...`。百度/谷歌的结果页**永远不会**有这种标记，
  所以即使哪天反爬解除、百度正常返回结果页，第 1 层也必然空手，
  只能退到第 2 层 h2/h3（browser_tools.py:196）——而百度/谷歌的结果标题
  结构（百度 `h3.t > a`、谷歌 `a > h3`）与该正则假设的
  `<h[23]><a href="http...">` 顺序并不匹配。也就是说：
  **这条路径目前即使不被反爬，也很可能解析不出结果。**
  本次我**没有实测到**这一点（因为被反爬挡住了，拿不到真 SERP），
  所以按任务要求我**不**把它报成"可为但解析器有 bug"——

3. **反爬是永久的还是 IP/频率相关的，我无法判定。** 
   本机此前多次探测过搜索引擎（仓库里有历史证据），
   当前 IP 可能已被标记。要做频率/时长实验（例如间隔数小时重试、换出口 IP）
   需要另一台机器或长时间窗口，超出本次范围。三次运行间隔 3 秒、
   结果逐字节相同，只能说明"在这个时间窗内是确定性拦截"，
   **不能**外推成"任何时刻任何 IP 都不可为"。

4. **谷歌那 92KB 里是否含"被服务端裁掉结果"的证据，我没有逐脚本反混淆。** 
   我只做到：可见正文 58 字符 + 结果容器计数全 0 + enablejs 钩子。

   如果结果其实以某段 JSON 内联在脚本里，那结论会从"反爬"变成"需要新解析器"——
   这需要更深的逆向工作，我**没有做**，所以留一个明确的未知。

5. **我只测了查询词「上海天气」一个词。** 不排除特定查询词表现不同
