P4-C2：ASR medium 档评估 —— 结论是「medium 在这个子集上不占优」
═══════════════════════════════════════════════════════════════

【零】先纠正一个我上一轮留下的错数字
--------------------------------------------------------------
P4-B5 证据里写的「加偏置后 24/24、空输出 0、听错 0」是**单次运行**的结果。
本轮复测（同命令、同参数）得到 **22/24、空输出 2**。
原因正是 P4-C1 查明的**替身抖动**：每次合成的音频样点不同，同一句在不同次运行
会被听成不同结果。所以下文一律报**区间/多格对比**，不报单点定值。

【一】四格对比（`--short 4`，每句 4 次 × 6 句 = 24 次；TTS 替身）
--------------------------------------------------------------
| 配置 | 正识 | 空输出 | 听错 | 误触发 |
|------|------|--------|------|--------|
| small，无偏置 | 18/24 | 2 | 4 | —（当时判据有错，见【三】） |
| **small + 偏置** | **22/24** | 2 | **0** | **0/16** |
| medium，无偏置 | **14/24** | **7** | 3 | —（同上） |
| **medium + 偏置** | **22/24** | 2 | **0** | **0/16** |

三条结论：

1. **偏置是决定性因素**：它把 small 从 18 抬到 22、把 medium 从 14 抬到 22，
   并且把两者的**听错都清零**（4→0、3→0）。
2. **medium 无偏置时明显比 small 差**：14/24 vs 18/24，而且**整句被丢**从 2 次涨到 7 次。
   逐句看最刺眼的是「停止」：small 4/4 → medium **0/4**（2 次被丢、2 次被听成「品质」「平址」）。
3. **加偏置后两者打平**（都是 22/24）。

【二】由此得出的建议（以及**不建议**做的事）
--------------------------------------------------------------
- ✅ **保留 `initial_prompt`**：它是把 18→22 / 14→22 的那个因素，且误触发 0/16。
- ⚠️ **不建议据此改 `model_size`**。理由是本轮只测了**6 句短确认语**这个子集。
  medium 在**长句**上未必更差（更大模型通常在长语音上更准），而我没测长句。
  「短句子集上 medium 不占优」**推不出**「该把默认档改成 small」。
- 若要真正决定档位，需要的是**长句 + 短句混合**的对比测量，并把加载时间/内存算进去
  （medium 权重 ~1.5GB，冷启动明显更慢）。这属于下一轮，不在本任务范围。

【三】⚠️ 我自己的测量工具错了一次（而且错得很有代表性）
--------------------------------------------------------------
"对照段"（测"偏置会不会把别的话拉成确认语"）第一版用朴素子串 `p in norm` 判断，
于是「你好呀」因含单字「好」被报成"被拉成确认语"，得出**误触发 4/16**。

**双重错误**：
1. 那个子串缺陷属于**路由侧**，P4-B5 已经修掉（改为"确认从严、取消从宽"）；
   测量工具却仍用旧判据 → **报出一个产品已经不会犯的错**。
2. 它把这个假象记在了"**解码偏置的副作用**"账上 → 会让人以为偏置有害。

修法：`_matches_phrase` 改为调用**产品的真实判据**
（`RuleRouter._matches_any(norm, CANCEL_PHRASES)` 与 `(..., CONFIRM_PHRASES, strict=True)`）。
修后自检：日常话（你好呀/我很好/好奇怪/好久不见/今天天气怎么样/打开浏览器）全部 False，
真确认语（确定/算了/嗯/好的，删吧）全部 True。
重测结果：small 与 medium 误触发均 **0/16** ⇒ 偏置**没有**把别的话拉过去。

教训同 §16.4：**测量工具必须调用被测系统本身的判定，不能自己复刻一份。**

P4-C3：sentence-transformers 真模型验证（此前从未下载过）
═══════════════════════════════════════════════════════════════

【零】为什么这条重要
--------------------------------------------------------------
此前 ST 嵌入器只用**假模块**测过（成功/失败/编码异常/维度探测/并发加载/close 重载），
**真模型上的 encode 归一化从未验证** —— 「向量归一化」一直只是纸面承诺。
本任务下载真模型并按 `p4-plan.md` 的验收条件实测。

【一】命令与结果：**8/8 通过**
--------------------------------------------------------------
命令：`python tools/_tmp_c3_st_real.py`（`SentenceTransformerEmbedder("all-MiniLM-L6-v2")`）

| 检查 | 结果 |
|------|------|
| 懒加载前 `ready()` 必须是 False | PASS |
| 加载后 `ready()` 必须变 True | PASS |
| 维度必须是非零实数 | PASS（**384**） |
| 每条向量维度 == 申报维度 | PASS |
| **向量必须已归一化**（\|‖v‖−1\| < 1e-3） | **PASS：两条实测 L2 范数均为 1.000000** |
| 同义句相似度 > 无关句（真语义能力） | PASS：余弦 **0.7655**（同义）vs **0.5561**（无关） |
| `close()` 后 `ready()` 回到 False | PASS |
| `close()` 后仍可再次懒加载 | PASS |

首次 `embed()` 耗时 **51198ms**（含下载 + 模型加载）；真实维度 **384**。
（config 的 `agent.memory.dim: 256` 与此**不冲突**：256 是默认 `hashing` 嵌入器的维度。）

【二】顺带修掉一个**真实的过期 API**（真模型才暴露出来）
--------------------------------------------------------------
真模型加载时打出：`FutureWarning: The get_sentence_embedding_dimension method has been
renamed to get_embedding_dimension`。

我们自己的 `st_embedder._detect_dim()` 只认**旧名字**。危害不是警告本身，而是：
将来旧名字被删 → 探不到维度 → `dim` **静默退回 `fallback_dim`** →
**vec0 索引按错误宽度建表**。假模块永远测不到这件事（假模块用的就是旧名字）。

修法：两个名字都试、**新的优先**；并新增 2 条用例
（"只有新名字"必须被采纳、"两个都在时新的优先"）。

【三】顺带核实的命名差异（避免下次踩）
--------------------------------------------------------------
本机 HF 缓存里原有 `Qdrant/all-MiniLM-L6-v2-onnx`（91.1 MB），
而 config 写的是 `all-MiniLM-L6-v2`。**两者不是同一个仓库** ——
ST 实际下载并加载的是 `sentence-transformers/all-MiniLM-L6-v2`。
"So 缓存里有 MiniLM" 不等于 "ST 的模型已经就位"。

【四】仍然没做 / 未验证
--------------------------------------------------------------
1. **未把 `agent.memory.embedder` 切成 `st` 跑端到端**：本任务验证的是**组件**，
   没验证"记忆检索用真语义嵌入后召回质量变好多少"（那需要一组带标注的检索样例）。
2. **未测真模型在 vec0 索引下的写入/检索**（维度从 256 变 384 会重建索引，
   这条路径只有假模块覆盖过）。
3. ST 首次加载 51s —— 若真在生产启用，需要评估这 51s 落在哪个时机（懒加载时会不会卡住用户请求）。
4. `--synth` / `--short` 的数字全部来自 **TTS 替身**，不是真人（同 P4-B5 的边界）。
