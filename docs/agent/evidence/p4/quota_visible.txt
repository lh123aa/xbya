【四】★ 补写证据时抓到的真实缺陷：`get_status()` 会被"自报异常的插件"打崩
--------------------------------------------------------------
`p4-plan.md` 的验收条件里有一条：**"状态面健壮 —— 插件自报异常时状态查询不得崩
（如实报 None / error）"**。原实现只做到了一半：

- `llm_capability()` **做了**保护（`try/except` 包住 `is_available()` 与 `quota_stats()`）；
- 但 `get_status()` 里插件状态循环那一行 `plugin.is_available()` **完全没有保护**。

而 `tests/test_app.py::test_llm_capability_survives_broken_plugin` 只调了
`llm_capability()` —— 于是那条用例**绿着**，而 `get_status()` 用**同款桩**直接抛
`RuntimeError: boom`。实测复现（`tools/_tmp_b3_getstatus.py`，修复前）：

```
  **崩了** 方法抛异常（同款桩）      RuntimeError: boom
  **崩了** 属性访问也抛（敌意桩）     RuntimeError: boom
  对照：llm_capability() 单独调     OK -> available=None quota_error='RuntimeError: boom'
```

修法两条：
1. `get_status()` 的插件状态循环改为 `try/except`，如实记
   `{"available": None, "error": "RuntimeError: boom"}`；
2. 新增 `_safe_hasattr()` —— Python 的 `hasattr` **只吞 `AttributeError`**，
   若 `__getattr__`/property 抛别的异常，`hasattr` 会把异常原样抛出，
   它本身就是帮凶；`llm_capability()` 里的两处 `hasattr` 也一并加固。
3. `status["llm"] = self.llm_capability()` 外面再包一层 —— 敌意桩仍可能从那里抛出来；
   状态面宁可少给一个字段，也不能整个查不出来。

> **还有一处是修的过程中才发现的**：第一版修法用
> `available = plugin.is_available() if _safe_hasattr(...) else True`，
> 结果敌意桩被报成 **`available: True`** —— 因为 `hasattr` 吞掉异常后，
> **"没有这个属性"与"取属性时炸了"变得无法区分**。
> 改为 `getattr(plugin, "is_available", None)`：默认值只在"确实没有"时生效，
> 取属性抛异常会走进 `except`。**报"可用"比报"不知道"危险得多**，
> 这条是我自己的测试（`test_get_status_survives_hostile_plugin`）逼出来的。

新增用例（`tests/test_app.py`）：
- `test_get_status_survives_broken_plugin_methods` —— 同款桩调 `get_status()` 不得崩
- `test_get_status_survives_hostile_plugin` —— 属性访问也抛的敌意桩不得崩，
  且**不得被报成 available=True**
