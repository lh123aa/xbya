【P5-C1 · 轮换前基线】docs/agent/evidence/p5/key_rotation.txt

探针只打印 key 的长度与前缀类别，并再做一次正则兜底 —— 文件里不含任何 key 内容。

三条实测（都逼的是产品自己的代码路径，不是我另写请求）：
  1. **两把 key 现在都还活着** —— 所以 C1 是安全卫生问题，不是停机抢修：
     · 主（Groq）报 `429 Rate limit reached`，**不是** 401/403 ⇒ key 有效、额度用尽
     · 备（OpenRouter）：把主 key 换成无效值后**成功降级并拿到回复**
  2. **轮换要改三处，只改一处会白改**：`cloud.api_key` **覆盖** `params.api_key`
     （实测 `core/plugin_params.plugin_params()` 的返回值取自 cloud）。
     只改 `params.api_key` 的话，生效的仍是被泄露的旧 key ——
     这种「改了但没生效」必须先写在证据里，否则轮换动作是假的。
  3. **降级路径上的 function calling 是通的**（本轮最有价值的一条）：
     把主 key 换成无效值逼出降级后，`chat_with_tools()` 返回
     `{'name': 'file_search', 'arguments': {...}}`。
     这条平时不会走到，**只有主 key 限流时才依赖**，正是「平时绿的、出事才发现坏了」
     的典型；D16 教过这个函数接错就静默失效（返回 None → 调用方读成「模型用文字回答」）。
