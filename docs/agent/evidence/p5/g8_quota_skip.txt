 一、缺陷 1：工具调用断言不查配额（产品侧，已修）
──────────────────────────────────────────────────────────────────────────────

位置：`tools/verify_f3_real_llm.py` 的 `[F3-a]` 段。

原写法：

```python
probe = app.route_with_tools(..., ..., TOOL_SCHEMAS)
check(probe is not None and probe.get("name"), "真实函数调用返回了工具名", ...)
check(probe and probe.get("name") in [...], "选中的工具在 schema 清单内")
```

`route_with_tools` 在 429 用尽重试后返回 `None` ⇒ 两条断言直接 FAIL。
而同文件的规划器那条早就这么写了：

```python
skipped(f"LLM 拆出了多步计划...", "3 次全部失败，但抓到 429/限流：... —— 外部配额")
```

⇒ **同一个病只治了一半**：`_QuotaWatch` 在 P4 缺陷 18 时建好了，
规划器接了，工具调用没接。

修法：调用前后各记一次 `len(quota.hits)`，
只有「返回 None **且**这次调用期间真的抓到 429」才降级为 SKIP：

```python
_hits_before = len(quota.hits)
probe = app.route_with_tools(...)
_quota_hit_here = len(quota.hits) > _hits_before
if probe is None and _quota_hit_here:
    skipped(...)   # 外部配额，不是本层结论
else:
    check(...)     # 照旧判 PASS/FAIL
```

 二、缺陷 2：验收脚本替自己做不成立的声明（更要紧）
──────────────────────────────────────────────────────────────────────────────

同一次运行（16/18 那次）的末段印着：

> 凡受此影响的断言都已归入 [SKIP]，**没有**被算成通过

而那次运行里明明有 **2 个 FAIL**，且它们正是配额造成的。
也就是说：**这句话当时是假的**。

为什么把这条排在前面：它不是「某个断言判错了」，而是
**给读者一个与事实相反的整体印象** —— 与 P4 那 7 处「检查本身出错」同族，
也与本项目一路在防的「纸面满足」同族。

修完缺陷 1 之后，这句话才真正成立（改动后配额恢复的重跑里就是 0 FAIL / 1 SKIP）。

 三、反方向核查：新分支不是死代码，也没把真失败洗成跳过
──────────────────────────────────────────────────────────────────────────────

429 不能按需制造，所以「改完没报错」**不能**当作「分支会走」。
本文件带一支探针，把**真正有疑问的那一点**确定性地测掉：
`_QuotaWatch` 到底把什么认成配额。
