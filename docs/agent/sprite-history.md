## D27 抠图边缘毛刺 + 裙子镂空 + 臂腰间隙被填满

✅ **已修（换新立绘那一轮，含一次自我纠正）**

**真正的根因有两层：**

① `build_base()` 结尾的 `np.where(alpha > 128, 255, 0)` 把 LANCZOS 抗锯齿
压成 0/255 → 128px 精灵上的阶梯毛刺（旧底图实测 **alpha 唯一值 = 2、
半透明像素 = 0**）。

② **我一度误判源图是"无 alpha 的白底图"**，于是用白底色键 + 边界泛洪
**重算 alpha**，反而制造了两个新破坏：
- **白裙子被打穿**（裙子高光 ~245 距纯白只有 10，色键判成背景）
- **胳膊与腰之间的镂空被填满**（那处背景被手臂和身体围住、
  不与画布外边界连通，泛洪不认它是背景）

用户指出"我已经是扣好图的 png 图，按 png 抠图结果为准"后核对：
源图**本来就是带 alpha 的 PNG**（256 个 alpha 值 / 58.0% 全透明 /
40.6% 不透明 / **1.39% 半透明** —— 那 1.39% 正是画师做好的抗锯齿边）。

**修法**：新增 `cutout_source_alpha()` 与 `keyer: "alpha"`（默认），
**有现成 alpha 就用它，绝不重算**；`white`/`rembg` 降为
"源图确实没有 alpha 时"的备用路径。

**教训**：抠图方式应由"源图有没有 alpha"决定，
不是由"背景看起来是什么颜色"决定。

**验收**：
1. 裙子中心带 x[51..76] y[128..257] **最小 alpha = 255、不透明率 100%**
2. 臂腰镂空左侧连续 242 行 / 右侧 240 行
3. alpha 唯一值 **249**（抗锯齿在）

三个判据脚本化。

## D29 点头幅度过大 + 两个动画其实是"死的"

✅ **已修**

用户反馈"头部点头的幅度调小一些"，量下去却查出**两个更严重的问题**。

**① 真正可见的是纵向位移，不是旋转。**
`f_listen` 的 `nod` 旋转量实测极差只有 **0.088°**（几乎不可见），
而 `breath_y` 是 **4.00 px**。调幅度必须调后者；只调 `nod` 的系数完全没有效果
（我第一版差点调错）。

**② `listen`/`sleep` 是唯一的两个 4.00px**，其余 6 个动画都在 1.0~2.0px：

| 动画 | 调前 | 调后 |
|------|------|------|
| idle | 1.95 | **1.46** |
| listen | **4.00** | **1.00** |
| sleep | **4.00** | **1.00** |
| think | 1.60 | 1.60 |
| happy | 1.71 | 1.71 |
| sad | 1.20 | 1.20 |
| stare | 1.60 | 1.60 |
| dance | 1.04 | 1.04 |

在 128px 宽的角色上，4px = **整个人上下跳 3%**；倾听是个持续状态，
长时间挂着会显得"坐不住"。

**③ 顺带查出两个动画是死的。**
`_shift()` 是**整像素**的（`int(round(dy))`），而：
- `f_sleep` 原式 `1.2 - 2.0*sin` 值域 [−0.8, 3.2]
- `f_sad` 原式 `1.8 + 0.6*sin` 值域 [1.2, 2.4]

两者**恒为正**，取整后**每一帧都是同一个值**，与静止参考帧做整数互相关
实测 `dy 全为 0`，整段动画**僵硬不动**。

**教训**：`transform()` 的位移是整数像素，任何"姿态偏移"若写成常量
（每帧相同）就等于没有动画；**逐帧摆动必须围绕 0**。

**修法**：`f_listen` 呼吸 ±2.0→±1.0、nod 0.095→0.075；
`f_sleep` 改 `-1.0*sin`（围绕 0）、`f_sad` 改 `0.7*sin`（围绕 0）；
`f_idle` 1.95→1.46px。

**验收**（脚本化，用整数互相关测真实位移档位）：八种动画全部落在 **1~2px**、
且**每个都有 ≥2 个位移档位**（不再是死的）—— idle/listen/sleep/sad/stare/dance
为 `[−1,0]`、think 为 `[0,+1]`、happy 为 `[−2,−1,0]`。
判据写法本身也可复用：**"位移档位只有 1 个"就是死动画**。

## D30 字幕不显示（跨线程投递被静默丢弃）

✅ **已修**

用户反馈"这个版本不显示字幕了"。

**根因**：`PetWindow._invoke_on_main` 用 `QTimer.singleShot(0, fn)` 做跨线程投递，
但 Qt 会在**调用线程**上创建那个定时器 —— 工作线程没有事件循环，
**回调被静默丢弃**。

**受控实验**（同一份代码、只换调用线程）：

```
主线程调用   → 回调执行 1 次  ✓
后台线程调用 → 回调执行 0 次  ✗
```

而真实链路上语音管线 / Agent 结果回调 / `_speak_sentences`
**全都在后台线程**里调 `show_bubble()` ⇒ **字幕永不显示**，
且日志一切正常（无报错、TTS 照常播放）。

**修法**：改用 `QMetaObject.invokeMethod(self, fn, Qt.QueuedConnection)`
（把调用排进目标对象所在线程的事件队列，跨线程投递有保证），
并保留"异常时退回直接调用"的兜底。

**为什么测试没抓到**：原 `test_show_bubble` 是在**主线程**里调的，
走的是 `_is_main_thread()` 直连分支，压根没进 QTimer 那条路 ——
**测试覆盖的是"简单的那条路"**。

**新增 2 条守护用例**：
1. `test_show_bubble_from_background_thread_lands`
   （从后台线程调 → 处理事件循环后 `bubble_text` 必须变成目标文本）
2. `test_invoke_on_main_uses_queued_connection`
   （monkeypatch 掉 `QTimer.singleShot`，断言它**不再被用于跨线程投递**）

**反方向验证过**：把 `QTimer.singleShot(0, fn)` 塞回去 →
**两条用例都变红**（`2 failed`）。

**定位手法也值得复用**：先做了 6 种"从窗口外面看"的尝试
（截图数像素、Qt `grab()`、offscreen/真实平台对照）**全部通过**，
因为问题根本不在绘制；最后给 `_draw_subtitle`/`paintEvent`
**装进程内探针**打印真实调用次数与 `bubble_text`，才看到
`_draw_subtitle 调用 0 次` 这个决定性证据 ——
**当"从外面测都对"时，要进进程内打点**。

修后同一探针：`_draw_subtitle 累计调用 43 次`、`bubble_text='🎧 在听…'`。
全量回归 **2839 passed / 1 skipped / 0 failed**。

## D31 位置记忆写进"屏幕外坐标"＋ VRM 模式整段跳过恢复

✅ **已修**（用户反馈"每次启动位置是上次关闭的位置，有时重启位置就跑到屏幕左上角了"）

**三处独立缺陷，症状都是"重启后位置不对/找不到桌宠"：**

① `_edge_snap()` 先把窗口移到屏幕外（右边只剩 8px 手柄），
`mouseReleaseEvent` 紧接着 `_save_position()` **无条件**存下这个坐标
—— **实测存进 `(1911, 300)`**。

② `_restore_position` 的判据**单向**：只挡 `x >= right-10` / `y >= bottom-10`，
**没有**左边/上边检查。

③ `load_pet` 在 `render_mode == "vrm"` 时**提前 return**，恢复整段跳过，
窗口停在 `__init__` 的 `(0,0)` —— 正是用户描述的"左上角"。

**修复**：`_pre_snap_pos` 记吸附前位置供存档用；新增**对称**判据
`_is_position_usable()`（按**所有屏幕**算可见交集，要求 ≥60px）；
VRM 分支补上恢复；另加两道闸（恢复完成前不写、贴边态不写屏幕外坐标）。

**端到端实测**（真启动应用）：

| 场景 | 结果 |
|------|------|
| 合法存档 `(760,366)` | → 原样恢复 ✅ |
| 屏幕外存档 `(-900,100)` | → 落到**可见**的 `(1631,120)` ✅ |
| 拖到右边缘贴边后重启 | → 恢复到拖拽处 `(1687,300)` ✅ |

同一场景下 HEAD 旧代码存的是 `(1911,300)`。

**⚠️ 差点交付一个假绿用例**：「判据对称性」那条测试起初在**旧代码下也是绿的**
—— 因为本机主屏 `left=0`，旧实现那句 `x<0` 会**碰巧**挡住贴左边的坐标。
写了个真值对比脚本才定位到：真正的单向性缺陷只在屏幕 `left>0`
（左侧挂副屏）时暴露。改成**注入屏幕几何**后，用例在旧实现下确实变红。

**留下的判据**：多屏相关的判据不要依赖本机布局 —— 本机恰好成立的巧合
会让缺陷"看起来不存在"；**把屏幕几何注入进去**，用例才与机器无关。

## D32 字幕动态更新（整段闪现后被逐句擦成碎片／控制标记漏屏／截断无提示）

✅ **已修**（用户反馈"字幕动态更新没有做好"）

**三处独立缺陷：**

① 播放线程**逐句覆盖且不带上一句**。实测时间线：

```
@0.75s  '今天天气不错，适合出门走走。记得带把伞，下午可能有阵雨。'   ← 整段闪现
@1.56s  '今天天气不错，适合出门走走。'                            ← 被切碎
@2.96s  '记得带把伞，下午可能有阵雨。'                            ← 上一句没了
```

观感是"整段闪现再被切碎重播"，而不是"滚动"。

② `_sanitize_text` 只清 markdown，**不清 `[silent]` / `[thinking]` 等内部控制标记**
—— 脏字直接上屏。真实日志里抓到的原文：

```
[emotion] 回复情绪: talk → 动效: talk (文本: [silent]嗯嗯。...)
[emotion] 回复情绪: talk → 动效: talk (文本: [thinking] 用户说"没用啊"...)
```

③ `_wrap_text` 达最大行数时调 `_clamp_line(…, ellipsis=True)`，
而该函数在"该行**本来就放得下**"时**原样返回、不加 …**
⇒ 超出部分被**静默丢弃且无提示**，用户以为那是完整回复。

**修复**：播放线程改为**滚动窗口**（当前句 + 上一句）。实测：

```
@1.70s  '今天天气不错，适合出门走走。'
@3.02s  '今天天气不错，适合出门走走。记得带把伞，下午可能有阵雨。'   ← 带衔接
@4.31s  '记得带把伞，下午可能有阵雨。路上小心点呀。'               ← 窗口滑动
```

**为什么不是"只显示当前句"**：每句把上一句擦掉，用户读到一半就没了。
**为什么不是"一直累积全文"**：窗口只有 228px 宽、字幕区 44px 高（最多 2 行），
累积会立刻溢出、后两行永远看不到。折中取最近两句。

清洗新增控制标记规则（**普通方括号与 markdown 链接不受影响** ——
`保留[普通方括号]内容` 原样保留，`[链接](url)` 仍正确剥成 `链接`）；
截断分支显式补 `…` 且保证不超宽（实测 207 ≤ 212）。

**顺带删掉一处死代码**：循环末尾的截断分支**结构上不可达** ——
第 2 次 `append` 前必然命中提前 return。穷举验证：6 字字母表、长度 1~6
共 **55986** 个文本 + 4000 个长随机样本，提前返回分支命中**全部**截断，
末尾分支命中 **0** 次。删掉它，而不是留一段"看起来在防护"的代码。

**⚠️ 中途我改成"完全不预写全文"，被既有用例抓出真实回归**：
`tests/agent/test_integration.py` 两条用例断言结果到达时 `bubble_text` 非空。
它们抓得对 —— 静音 / TTS 全部失败 / 无 app 时，逐句播放链路**根本不会跑**，
正文就永远不显示（白屏）。最终改为"**先整段上屏 + 滚动窗口接管**"，两全。

**留下的判据**：

1. "先显示全文"本身不是缺陷，**"显示了却被无衔接地擦成碎片"才是** ——
   改之前先量清楚用户实际看到的**时间线**，别凭代码形状下结论；
2. 内部控制标记必须在**清洗层**统一剥掉，不能只在那一条调用路径上处理 ——
   否则换个分支就漏出去（这里正是"silent 分支清了、说话分支没清"）；
3. 被截断的内容**必须留下可见痕迹**（`…`）；静默丢弃比显示不全更糟；
4. 删掉不可达分支之前要**穷举证明**它不可达，而不是"看起来应该不会走到"。

## D33 麦克风关了还能听到声音（开关只改内存 + 闸门缺失）

✅ **已修**（用户报告："🎤 麦克风关了，她还能听见我说话并回应"）

**确认过程**（先问清楚是哪个开关，避免修错地方）：
右键菜单里有两个相邻但语义不同的开关 —— `🔊 声音`（实际只控制**她出不出声**，
完全不碰麦克风）与 `🎤 麦克风`（控制**输入**）。用户确认用的是后者。

**先排除的**：`🎤 麦克风` 本身的停止逻辑是**正确**的。实测（插桩在真实读循环里）：
关麦后 6 秒内**新增 0 个音频块**，`is_listening=False`，
且 `_force_resume_mic()`（看门狗链路）与 `_arm_echo_guard()`（播报收尾链路）
**都不会**把它重新打开。

**真正的两处缺陷：**

① **开关只改内存、不落盘。**
`_toggle_mic(False)` 只设 `self._monitor_enabled = False`，
**从来不写 `config.voice.listening`**。而配置里原本是 `listening: true`，于是：

- 之后任何一次「打开设置 → 保存」→ `apply_settings()` 按
  `voice.listening` **无条件重启监听** → **麦克风被重新打开**，菜单仍显示"已关闭"；
- **下一次启动**同理：配置里是 true，一启动就开始听。

用户的意图没有持久化，开关只是"这一次有效"。

② **捕获入口没有闸门。**
`_on_speech_captured()` **不检查 `_monitor_enabled`** —— 它只看 `_speaking`
和队列状态。只要底层流因为任何原因（竞态、重启、别的代码路径重新 open）
还活着，捕获到的语音就会被**正常处理并回应**。

**修复：**

- 开关动作**落盘**：新增 `_persist_listening()`，写失败只告警、**不破坏开关本身**
  （不能因为配置写不进去就让用户这一次的操作也失效）；
- 捕获入口加**用户意图闸门**：判据用 `_monitor_enabled`（**用户说过要关**），
  **不是**底层流状态 —— 流可能因竞态短暂存活，但用户意图必须永远优先；
- 热键 `toggle_voice_monitor()` 与菜单**收敛到同一条路径**（`_toggle_mic`），
  原先两处各写一份、行为不一致。

**测试**：`tests/test_mic_toggle_persist.py` 9 条 + **逐条反方向验证**
（三处修复分别退回 → 分别有 3 / 2 / 1 条用例变红，确认不是空转）。

**⚠️ 我在这一轮也误判了一次，值得记下来：**
第一版测量给出的结论是「关麦后麦克风仍继续采集约 **6 秒**」—— 看起来是个
更严重的 bug。但那是**测量假象**：我在 `listen_standby()` 之后只等 3 秒就关闭，
而本机设备挑选 + `p.open()` 要 **~6.2 秒**才进入读循环 ——
我测到的是"**还没开始读**"，不是"关不掉"。等到确实读到数据再关闭，
真实关闭延迟是 **~40ms**（只有 1 个在途 chunk）。

**留下的判据：**

1. 测量"某动作是否生效"之前，先确认**被测量的东西真的在运行** ——
   否则"没有变化"会被读成"关不掉"，而真相是"压根没开"；
2. **开关类功能的判据是"用户意图"，不是"底层状态"** ——
   两层都要落地：意图要持久化（扛得过重启与其他代码路径），
   执行要幂等（捕获入口按意图拒绝，而不是信任流状态）；
3. 同一个功能**只能有一条实现路径**（这里是热键与菜单各写一份 → 行为不一致）；
4. 配置写失败**不能连带破坏功能本身** —— 落盘是"记住"，不是"生效"的前提。

## D34 设置里的「人设提示词」没被加载（被 reply_style 分支绕过）

✅ **已修**（用户报告："后台设置中，人设设定好像没有真正的加载到虚拟人设角色中"）

**根因（一处，但很隐蔽）：**

`plugins/llm/openrouter/plugin.py` 的 `UniversalLLM.__init__` 按 `reply_style`
**二选一**挑 prompt：

```python
if reply_style == "detailed" and system_prompt_detailed:
    self.system_prompt = system_prompt_detailed
elif reply_style == "concise" and system_prompt_concise:
    self.system_prompt = system_prompt_concise     # ← 出厂走这条
else:
    self.system_prompt = system_prompt or "你是欣雅…"   # ← 用户写的人设只在这里用
```

而**设置界面编辑的字段正是 `system_prompt`**
（`settings_dialog.py:815`：`cfg.set("plugins.llm.params.system_prompt", …)`）。

出厂配置 `reply_style: concise` 且 `system_prompt_concise` 非空 ⇒
**用户写的整段人设永远走不到 `else` 分支，一个字都到不了模型。**

**实测数字（不是推测）：**

| | 字数 | 开头 |
|---|---|---|
| 设置里 `system_prompt` | **1935** | `北执，收到。既然你要创建一个属于你的"欣雅"…` |
| `system_prompt_concise`（实际生效） | **388** | `你是欣雅，25岁，住在用户电脑桌面上的温柔学霸小女生…` |
| 插件实例最终持有的 `system_prompt` | **388** | 同上 —— 证实用户那份被丢弃 |

构造真实插件实例验证：`inst.system_prompt` 长度 388，`user in inst.system_prompt == False`。

**修复（把"人设"与"详略"分开，各管各的）：**

- `system_prompt` = **人设本体**，无论详略都必须生效（这是用户在设置里能看见的东西）；
- `system_prompt_concise` / `system_prompt_detailed` = **详略指令**，
  作为**附加段**拼在人设之后，而**不是把人设替换掉**；
- 用户没写人设时才回退详略段（保持出厂行为不变）。

修复后实测：最终 system message **2330 字**，开头是用户那份人设，
结尾是 concise 详略段 —— 两者并存。

**影响面**：**只有 `openrouter` 插件有此缺陷**。
`openai_api` 与 `ollama` 一直是直接使用 `system_prompt`，没有这个分支。

**⚠️ 测试侧我踩了一个值得记下来的坑：**

第一版用例直接调 `UniversalLLM._compose_system_prompt(...)` 这个 helper
（因为它是纯函数、好测）。反向验证时，我把 `__init__` 里的选择逻辑
**退回旧实现**，结果 **9/10 条用例照样全绿** ——
因为 bug 在"**谁被调用**"这一层接线，而我测的是被调用的那个函数本身。

改为**经构造函数**（`UniversalLLM(**params).system_prompt`）后，
同一组回归立刻有 **4 条**变红。

**留下的判据：**

1. **"配置项存在" ≠ "配置项接线"** —— 这里的 `system_prompt` 确实被读、
   确实被存、确实被传进构造函数，却在一个二选一分支里被静默丢弃。
   排查这类问题要看**最终对象持有的值**，不是看"有没有读这个键"；
2. **同一概念有两个键、又有个分支去"选一个"时，必须问清楚"用户改的是哪个"** ——
   设置界面写 A、运行时用 B，是这类缺陷的通用形状；
3. **用例要钉住最终对象的状态，不能只测 helper** ——
   否则"谁被调用"的接线错误测不出来（这一条是用一次假绿换来的）；
4. 修"选择逻辑"时保留出厂行为：没写人设的用户，体验必须和以前一样。


## D35 TTS 完全没声音（"推荐音色"根本不存在）

✅ **已修**（用户报告："怎么又听不清了" —— 但**根因不在麦克风**）

**为什么第一轮会误判成麦克风问题：**

用户说"听不清"，直觉指向麦克风。实测日志里也确实有大量
ASR 垃圾输出（`好。` / `词曲 李宗盛`），看起来像"收音不对"。
**但同一份日志里还有 14 条 TTS 失败**，那才是"听不见"的真正原因 ——
**她根本没发出声音，不是"听不清"**。这条记下来是因为：
"听不清"这个描述同时指向"我说话她听不到"和"她说话我听不到"两个方向，
**必须先分清是哪一头**，否则会把一整轮花在健康的麦克风上。

**根因（一个臆造的音色名）：**

设置界面的音色菜单里，「🎀 晓伊 · 活泼可爱（欣雅推荐）」写的是
`zh-CN-xbyaNeural` —— **这个音色在 Edge TTS 根本不存在**。
它是把项目名 `xbya` 塞进 `zh-CN-<name>Neural` 这个模板**拼出来的假名字**，
不是从真实音色表里选的。

**它的危险之处在于"不报错"：**

Edge 对不存在的音色**不抛异常**，只返回**空音频流**。于是：

| 环节 | 表现 |
|------|------|
| 设置界面 | 能选中、能保存、无任何提示 ✅ 看起来正常 |
| 插件 | `logger.error("语音合成失败: No audio was received…")` ×14 |
| 用户 | **一个字都听不到** |

实测（独立探针，非推测）：14 个菜单音色逐个流式合成，
**13 个可用，只有 `zh-CN-xbyaNeural` 返回 0 字节**。

```
zh-CN-xbyaNeural           -> 异常 NoAudioReceived
zh-CN-XiaoxiaoNeural       -> 7200 字节
zh-CN-XiaoyiNeural         -> 8352 字节
```

**它是三个地方的默认值**，所以**什么都不改的用户默认就踩中**：

1. `ui/settings_dialog.py` 菜单里的"**推荐**"项（最容易被选中的那个）
2. `ui/settings_dialog.py` 的 fallback 默认值（两处）
3. `plugins/tts/edge_tts/plugin.py` 的 `__init__` 默认参数

**修复：**

- 音色改为真实存在的 `zh-CN-XiaoyiNeural`（晓伊 · 活泼可爱）；
- **插件新增「空音频判失败」守卫** —— 这条比改名更重要：
  即便将来又有人写错音色，也会立刻看到 `ERROR … 音色 'xxx' 可能不存在`，
  而不是拿到 `b""` 以为"合成成功但没声音"；
- `config.yaml` 同步修正（未跟踪，不进版本库）。

**真机验证**（启动完整应用，不改任何设置）：

| | 修复前 | 修复后 |
|---|---|---|
| TTS 成功 | **0** | **14** |
| TTS 失败 | 14 | **0** |
| 空音频 | — | **0** |

**测试**：新增 `tests/test_tts_voice_validity.py` **7 项** ——
菜单音色白名单校验、推荐项必须指向真实音色、全仓不许再出现假音色、
空音频必须判失败并打日志。

**反方向验证**（两处各做一次）：

- 把假音色塞回菜单 → **4 failed / 3 passed**
- 拿掉空音频守卫 → **1 failed / 6 passed**

恢复后均 **7 passed**。

**留下的判据：**

1. **"名字看起来对" ≠ "东西存在"** —— `zh-CN-xbyaNeural` 在形式上
   完全符合 Edge 的命名模板，所以能通过任何**格式**校验。
   凡是"把参数拼进模板"生成的名字，都必须拿**真实清单**核一遍，
   不能只核对格式；
2. **对"空结果"必须显式判失败** —— 外部服务对非法参数"不报错、
   只回空"是常见行为。拿到空就返回成功，会把参数错误伪装成
   "功能正常但没效果"，最难排查。**空 = 失败**，并且要**点名是哪个参数**；
3. **"推荐"项是默认路径** —— 被标注"推荐"的选项会被最多的人选到，
   它比其它选项更必须被实测过；把它当默认值写进代码更要实测；
4. 排障时**先把"没说"和"没听见"分开** —— 同一句"听不清"覆盖两头，
   看日志时先确认**哪一头是断的**。


## D36~D43 语音互动管线端到端监督分析（一次系统排查）

用户报告："整个语音互动管线好像出问题了，要么听不到，要么听不清，
要么听到半天不回复，回复语音又不发声，有时候还答非所问"。

要求"驾驭工程，监督分析检查问题所在原因，给出解决方案"。
以下是逐阶段量化的结果 —— **先量再改，不猜**。

### 方法：把管线拆成 6 段，用真实日志量通过率

工具 `tools/audit_voice_funnel.py` 输出（131 秒真实样本）：

| 阶段 | 数量 | 通过率 |
|------|------|--------|
| ① 触发（超过阈值） | 18 | — |
| ② 捕获（录完交付） | 18 | 100% |
| ③ ASR 出文本 | 9 | 50% |
| ④ 送进 Agent/对话 | **1** | **★ 11%** |
| ⑤ LLM 回复成功 | 1 | 100% |
| ⑥ TTS 合成（含预热 14） | 16 | — |
| ⑦ 看门狗强制解锁 | 1 | — |

**漏斗在 ③→④ 断掉：9 条识别结果里 8 条凭空消失**，而日志从
`ASR 耗时 xxxms` 直接跳到下一轮 `暂停监听` ——
没有入队、没有丢弃、没有转 Agent，**一片安静**。

### 五类症状的定位结果

| 症状 | 真实根因 | 性质 |
|------|---------|------|
| **听不到** | 麦克风输入电平只有正常值的 **1/25**（满量程 1.66% vs 正常几十个百分点） | **硬件/系统**，见下 |
| **听不清** | ASR 输入是背景音（8/9 是同一个词 `好`） | 输入污染 |
| **不回复** | 8/9 条被 `_should_ignore`（长度<3）与 `_is_real_speech` **静默丢弃** | ✅ **代码缺陷，已修** |
| **回复不发声** | 实测 TTS 合成 + pygame 播放**均正常**；16 次合成里 14 次是 ack 预热 | 非缺陷 |
| **答非所问** | 听到 `词曲 李宗盛` 就答"这里写：词曲：李宗盛" —— **一一对应** | 非缺陷，她答得对 |
| **半天不回复** | 备用模型是**推理型**，每次先吐 500~800 字思维链才给 6~31 字正文 | ✅ **已修**（换 mini 变体 8.76s → 1.03s） |

**最重要的澄清**：「答非所问」**不是她理解错了** —— 把她听到的与她的回答
并排，每条都对得上。她听到的是电视字幕，答得非常准确。
**是输入被电视污染了。**

### 逐项修复

**D40 静默丢弃（"不回复"）**
`_voice_pipeline` 在 ASR 之后串了两个过滤器，**两条都是静默 return**。
`_should_ignore` 用 `voice.reply_min_length`（出厂 3）卡长度，
而 `好` 只有 1 个字 → 必然被拦；本机 ASR 最常输出的恰是这类短词。
修复：两条出口都补 INFO 日志，说明**被哪条规则、因为什么、怎么改**。
反方向验证：移除 4 处日志 → 3 条变红。

**D41 备用模型太慢（"半天不回复"）**
受控端到端实测：`① 测激 → ② ASR 709ms ✓ → ③ LLM 13.24s ✗ → ④ TTS 1.81s ✓`。
**LLM 一段占掉 13 秒**。根因是 Groq 配额耗尽后每次都走备用，
而备用 `nex-n2.5-pro:free` 是推理型，实测平均 **8.76s**、最慢 17.29s。
换成 `nex-n2.5-mini:free`（实测平均 **1.03s**）后：**13.24s → 3.66s**。

**D42 配置指向了近乎死流的设备**
之前把 `mic_device` 定成 7，依据是**单次**探测。用"数据是否在变"复测：

| 轮次 | idx=1 | idx=7 |
|------|-------|-------|
| 1 | 变化 17/18 ✓ | 变化 5/18 ✗ |
| 2 | 变化 17/18 ✓ | 变化 6/18 ✗ |
| 3 | 变化 17/18 ✓ | 变化 9/18 ✗ |

**14 个设备里只有 2 个真的活着。** 改为 idx=1 后：
底噪 4346→**92**，阈值 27012→**216**，死流恢复 16 次→**0 次**。

**判据教训**：本次反复被三种"看起来全正常"的假活状态误导 ——
① 能打开但恒返回 0（被误读成"环境安静"）；
② 能打开但返回**重复缓冲**（幅度不小，被误读成"在工作"）；
③ 不同 idx 读数**逐位相同**（被误读成"两设备一致"）。
**正确判据只有一条：数据在不在变。**

**D43 增益补偿位置错误（"听不到"的关键）**
ASR 插件自带 30x 增益，但只在**录音完成之后**生效 ——
而触发判断用的是补偿前的电平，链路根本走不到录音那一步。
修复：把补偿提到**触发判断之前**（新增 `voice.mic_gain`，默认 1.0
与原行为一致，上限 50x）。
效果：触发 **0 → 15 次**。

⚠️ **但触发了仍然捕获不到** —— 卡在 `早退B`：

    早退B：动态范围不足 (峰 469 / 谷 256 = 1.8x < 2.5)，疑似背景音频

**关键认识：等比增益改变不了峰谷比。**
峰与谷同时放大 2.5 倍，比值不变（1.84x → 1.83x）。
实测 5 次全部落在 1.4~2.0x，无一达到 2.5x。

**所以最终根因是麦克风的信噪比**：信号太弱、被压在底噪附近，
峰谷比天然接近 1，而真人正常拾音是 3+。

### 结论：这不是代码能修的

三条独立证据一致指向**系统层面的输入增益过低**：

| 来源 | RMS | 峰值 | 满量程 |
|------|-----|------|--------|
| 用户对着麦克风说话 | 116 | 544 | **1.66%** |
| 扬声器外放（已知很响） | 131 | 649 | **2.00%** |
| 回环测激（ASR 能正确识别） | 2867 | 22593 | 69% |

扬声器这么响的声音录进来也只有 2% → **不是"麦克风离得远"**，
而是输入增益本身被压到了极低。

**用户操作建议**（按优先级）：
1. Windows 声音设置 → 输入 → 麦克风 → 音量调到最大；关掉降噪
   （降噪会把弱信号压得更平，峰谷比更差）
2. 换离嘴更近的麦克风（耳机麦）；距离每减半，幅度约翻倍
3. 台式机检查是否插在前面板（前置口增益常明显低于后置）

`tools/audit_mic_gain.py` 可随时复跑，直接给出"满量程百分比"与
"说话/安静比值"，用于确认调整是否生效。

### 留下的可复用判据

1. **"能打开"不等于"有信号"** —— 判活性的唯一标准是**数据在变**；
2. **改参数前先确认它在链路里的位置** —— 增益放在阈值判断之后就等于没放；
3. **等比增益不改变比值** —— 想解决"起伏不够"要用信噪比手段，
   不能用放大；
4. **"她答得不对"先查输入** —— 把识别文本与回复并排，多数"答非所问"
   是输入本身错了，不是模型理解错；
5. **静默丢弃是排查的头号敌人** —— 漏斗每一级都要能对上数，
   丢弃必须留下可读的理由；
6. **测量要控制变量** —— 顺序测量的两次读数不能直接比（比的是时间差），
   要**同时**采集才能归因到设备。


## D44 麦克风未拾取声音（三层判据 + 增益无效的实测）

**背景**：D43 的结论是"输入电平只有 1/25，是硬件问题"。
但**幅度低本身不等于不能用** —— 16bit 有 96dB 动态范围，只用 1.66%
也还有约 9.4 bit 有效精度。真正决定成败的是**信噪比**。
所以本轮做了三组受控实验来验证，而不是继续断言。

### 实验一：增益能否救回来？—— 不能

录一段真实说话，按 1/2/5/10/20/40 倍放大后分别喂 ASR：

| 增益 | 放大后峰值 | 削顶 | ASR 结果 |
|------|-----------|------|---------|
| 1x | 567 | 否 | None |
| 10x | 5670 | 否 | None |
| 40x | 22680 | 否 | None |

**任何增益都无法识别**，且都没削顶。本地 faster-whisper 同样返回空。
⇒ 软件增益解决不了。

工具：`tools/audit_gain_vs_asr.py`（可复跑）

### 实验二：录到的到底是不是人声？—— 不是

7 秒录音（前 2 秒静、中 3 秒说、后 2 秒静），按 0.5 秒切段看起来"有反应"：

    0.0-0.5s  55.8   （应安静）
    2.0-2.5s 151.5   （应说话）← 起来了
    4.5-5.0s 177.5   （应说话）← 最高
    6.5-7.0s 139.7   （应安静）

但**频谱判据**揭穿了它：

| 频段 | 说话段/安静段 |
|------|--------------|
| 低频 <300Hz | 1.02x |
| **人声 300-3400Hz** | **0.82x** ← 反而更低 |
| 高频 >3400Hz | 0.98x |

人声频段没有能量 —— 起伏只是**宽带噪声**，不是人在说话。

### 实验三：敲击响应 —— 没有任何设备有响应

敲麦克风会产生极明显的冲击，比"说话"更容易客观判定。
对 6 个可打开的设备各测"安静 2 秒 + 敲击 2 秒"：

| idx | 比值 | 判定 |
|-----|------|------|
| 0 | 1.15x | ✗ 无响应 |
| 1 | 1.00x | ✗ 无响应 |
| 7 | 1.00x | ✗ 无响应 |
| 8 | 1.00x | ✗ 无响应（且是死流：10 块只有 2 块不同） |
| 2 / 6 | 1.00x | ✗ 恒零 |

### 结论：三层判据逐层淘汰假象

| 层 | 判据 | 本机结果 |
|----|------|---------|
| L1 活性 | 数据在变 + 非零占比 > 50% | 14 个设备只有 2 个活着 |
| L2 响应 | 敲击时峰值 ≥1.5x | **全部 1.00~1.15x** |
| L3 人声 | 人声频段 > 1.3x | **0.82x（低于安静段）** |

三层都不过 —— 采集流在跑，但**物理麦克风没有把声音送进来**。
**代码无法修复**，需要用户从系统层面解决。

### 交付物

  · `tools/audit_voice_input.py` —— 一键诊断，输出三层判据 + 5 项检查清单
  · `tests/test_voice_input_criteria.py` **8 项** —— 把三层判据固化成用例，
    含"等比放大不改变频段比值"这条结论（说明增益救不了信噪比）

### 用户操作清单（按优先级）

1. 笔记本/键盘的**麦克风静音键**（常有指示灯）
2. Windows 设置 → 隐私 → 麦克风 → 允许桌面应用访问
3. 声音设置 → 输入 → 设备属性 → **音量是否被拉到 0**
4. 是否插着**耳机**（插上后内置麦常被自动禁用）
5. USB/蓝牙麦克风是否真的连上了

调整后复跑 `python tools/audit_voice_input.py`：
**L2 敲击响应 ≥1.5x** 就是好了。

### 留下的判据

7. **"幅度低"与"信噪比差"是两回事** —— 前者可以靠增益补救，
   后者不能。**判据是频谱，不是幅度**：人声频段（300-3400Hz）
   的能量必须显著高于安静段；
8. **敲击是最客观的输入测试** —— 它不依赖用户发音、不依赖 ASR、
   不依赖语言，一个比值就能判定"麦克风有没有把声音送进来"。


## D45 字幕与语音不同步（按字数估时长是错的方法）

**用户报告**："字幕和语音不同步，优化动态切换字幕"

### 量化：公式估的时长与真实音频差多少

原实现 `show_dur = max(2500, len(text)/4.0*1000 + 500)`
（"每字 250ms + 500ms 余量"）。用真实 TTS 音频实测对比：

| 句子 | 字数 | 公式估 | 实测 | 差 |
|------|------|--------|------|-----|
| 嗯嗯，我在呢，哥～ | 9 | 2750ms | 2760ms | -10ms |
| 哥，我还不能实时查到准确天气呢 | 16 | 4500ms | 3984ms | **+516ms** |
| 你在哪个城市呀？… | 24 | 6500ms | 5760ms | **+740ms** |
| 好呀，哥，我都记住啦。… | 30 | 8000ms | 7080ms | **+920ms** |
| 啊？ | 2 | 2500ms | 1440ms | **+1060ms** |

**5 句里 4 句差超过 500ms，最长 +1.1s** —— 字幕在语音播完后还挂着。

根因：**字数与时长不是线性关系**。语速、标点停顿、音色都会影响时长，
"啊？"两个字被估成 2.5 秒，而实际只读 1.44 秒。

### 修复

新增 `_audio_duration_ms()`，按优先级取**真实时长**：
  1. WAV 头解析（帧数/采样率）
  2. mutagen 解析 MP3
  3. **按已知比特率由字节数换算**（CBR MP3 字节数 ∝ 时长，
     比按字数准得多，且不受语速影响）
  4. 全都拿不到才退回按字数估算（行为不比原来差）

字幕停留 = 音频真实时长 + 300ms 余量。

实测：`啊？` 1440ms → 1368ms（旧公式 2500ms）；
长句 7080ms → 6744ms（旧公式 8000ms）。

工具：`tools/audit_subtitle_sync.py`（可复跑）

### 留下的判据

9. **"看起来合理"的公式也要实测校准** —— 按字数估时长读起来很自然，
   实测却 4/5 句超标。凡是"估算"，都要拿真实数据对一次；
10. **能拿到真值就不要估算** —— 音频时长是**可测的**（字节数/比特率），
    没有理由去猜。


## D46 闲聊被判成文件操作（三处缺陷叠加）

**用户报告**："她总是说『哎呀，刚才那个「Desktop」我没太听明白呢』，
我也没让他操作桌面软件呢"

### 日志证据

    file_list({'dirs': ['Desktop']}) conf=0.93
    目录解析失败: 不认识这些目录：Desktop
    可用的目录是：Desktop、Documents、Downloads、Pictures
    -> "「Desktop」这个位置我没听懂哦，我只能操作：Desktop、..."

**用户从没提过任何目录**，却被派了 `file_list` 并带上 `dirs=['Desktop']`。

### 三处缺陷（逐条实测复现）

**① 参数提取凭空造默认目录**

    return {"dirs": dirs or ["Desktop"]}      # <- 没说目录就默认 Desktop

"没说"被伪装成"说了 Desktop" —— **用户意图被静默替换**。
后果不止误判：他若真说"列出文件"，本意是"当前上下文"，
却被换成"列出桌面"。这是**猜**，不是**听**。

**② 关键词表里塞了日常口语**

`file_list` 关键词含 `"有什么"(2.2)`、`"看一下"(1.2)`，
基础 0.60 + 关键词 0.25 + 参数完整 0.15 ≈ 0.93。实测：

| 输入 | 误判 | 置信度 |
|------|------|--------|
| 今天有什么好吃的 | file_list | 0.93 |
| 你觉得我这个人有什么缺点 | file_list | 0.93 |
| 看一下我新买的鼠标 | file_list | 0.85 |

**③ 低置信的"动作类"意图会被执行**

HybridRouter 在 LLM 不可用时无条件 `return rule_cmd`，
0.25~0.33 置信度的猜测照样当指令执行。

### 修复

1. `_extract_list_params` 不再造默认值（没说就不填）；
2. 新增 `_NEEDS_TARGET_ACTIONS`：文件类动作**缺目标时强降分**
   （`conf = min(conf - 0.45, 0.35)`）。
   ⚠️ "目标"按动作取不同字段：`file_list` 看 `dirs`、
   `file_read` 看 `target`/`dirs`、`file_delete` 看 `targets`/`dirs`/`pattern`
   —— 第一版只查 `dirs`，把 `打开桌面上的报告.txt` 误降成 0.35，已修正；
3. HybridRouter 在 LLM 不可用且规则低置信时**动作类转 chat**
   （chat 无副作用，动作有副作用）。

### 效果（实测 9 条）

    闲聊 → chat：今天有什么好吃的(0.33) / 你觉得我这个人有什么缺点(0.33) /
                 看一下我新买的鼠标(0.25) / 我桌面上东西太多了(0.10)   全部 ✓
    真指令 → 动作：找一下桌面上的PDF文件 → file_search 0.99
                  删除桌面上的截图      → file_delete 0.95
                  列出下载目录里的文件   → file_list   0.99
                  打开桌面上的报告.txt   → file_read   0.93    全部 ✓

### 顺带修：白名单指向已删除的沙箱

    path_whitelist: [...\Temp\xbya_manual\Desktop, ...]

`xbya_manual` 是**人工验收留下的临时沙箱，早已不存在**，
四个目录全不存在 ⇒ 任何文件操作都会失败。
已清空配置、回退默认四目录（实测四个真实目录均存在）。

### ⚠️ 两条旧用例原先把缺陷固化成预期

  · `test_list_no_dir` 断言 `{"dirs": ["Desktop"]}`，注释写着"默认桌面"
  · `test_no_llm_provider` 断言 0.1 置信度的 `file_search` 被执行

两条都已改写为正确行为，并在 docstring 写明"这是在修正缺陷预期"。
**这是"测试全绿"最危险的一种形态** —— 用例本身在为缺陷背书。

**反方向验证**（逐个退回旧实现）：

| 退回的修复 | 变红用例数 |
|-----------|-----------|
| 恢复 `"dirs or [Desktop]"` | **8 failed** |
| 去掉缺目标降分 | **7 failed** |
| hybrid 低置信仍执行动作 | **6 failed** |
| 全部恢复 | 18 passed |

### 留下的判据

11. **默认值只能补"已确认的意图"，不能制造意图** ——
    `dirs or ["Desktop"]` 把"没说"变成"说了"，是最隐蔽的一类错误：
    它不报错、不缺参数，只是**替用户做了决定**；
12. **没把握时宁可当闲聊** —— `chat` 无副作用、动作有副作用。
    低置信猜测被执行，代价是用户看到"她从没被要求过"的操作；
13. **"测试全绿"可能是在为缺陷背书** —— 改行为前先看旧用例断言了什么，
    如果断言本身就是错的，要改的是用例并写明理由，而不是迁就它。

## D49 配置指向不存在的插件，且"没加载"的判据是 `is None`

**发现方式**：系统性功能完整性审计 —— `tools/audit_plugin_params.py`
（配置键 vs 构造函数签名）先报"类不存在"，再追到 `tools/audit_dead_engines.py`。

**证据全文**：`docs/agent/evidence/d49_dead_engines.md`

### 三层现象

| 层 | 现象 | 实测 |
|----|------|------|
| 1 | 配置里的引擎名指向**不存在的插件** | `plugins/embedding/embed_anything/` 与 `plugins/vector_db/leann/` 里**只有 0 字节 `__init__.py`**，**没有 `plugin.py`** |
| 2 | "降级到全文搜索"的判据**接不住空对象** | 加载失败拿到的是 `NullEmbedding` / `NullVectorDB`，**不是 `None`** ⇒ `is None` 永真不了 |
| 3 | 真正触发的分支**给不出归因** | 日志只有一句「查询向量化失败」，**没有一处说"因为配置写的引擎不存在"** |

`scan()` 的判据是"目录下有没有 `plugin.py`"（`core/plugin_loader.py:108`），
所以这两个目录**被整个跳过**——连"发现插件"的日志都不出现。

### 严重性：低（但必须修，理由可核对）

三条判据都是命令可复核的空结果：

| 判据 | 结果 | 命令 |
|------|------|------|
| `semantic_search()` 有生产调用者吗 | **0 个** | `git grep -n 'semantic_search' -- '*.py'` |
| `get_file_service()` 有调用者吗 | **0 个** | `git grep -n 'get_file_service' -- '*.py'` |
| `core/app.py` 用 `FileService` 吗 | **不用** | `Select-String -Path core\app.py -Pattern 'FileService'` |

即**整条子系统不可达**。修它的理由不是"用户正在受害"，而是
**配置在说谎**：下一个读配置的人会以为语义搜索可用。

### 修复

1. **配置不再说谎**：两个引擎显式置 `null`（`config.yaml` + `DEFAULT_CONFIG`）。
   语义是"本能力当前无后端"——这是事实；写一个不存在的引擎名是误导。
2. **判据换成问插件自己**：新增 `_embedding_unavailable()` / `_vector_db_unavailable()`，
   判 `is_available()`（空对象按契约返回 `False`），**不用 `is None`**。
3. **归因补上**：`FileService._degraded` 记下"哪个配置键、写的是什么、为什么失败"，
   降级日志点名它。

**实测（改前 → 改后）**：

```
改前: [ERROR] 查询向量化失败                     ← 没有归因
改后: [WARNING] 语义搜索不可用，改用全文搜索（原因：embedding:
      plugins.embedding.engine 写的是 'embed_anything'，但插件加载器里
      没有这个插件（要求目录下存在 plugin.py）；...）
```

**反方向验证（两次，都做了）**：

| 拆掉什么 | 结果 |
|---------|------|
| 判据退回 `is None` | `test_degrade_actually_calls_fulltext_search` + `test_degrade_warning_logs_the_reason` **2 failed** |
| 日志里的原因换成固定串 | `test_degrade_warning_logs_the_reason` **1 failed** |

注意红的是**接线用例**，不是"存在性用例"——这是刻意的：本文件既有 8 条里
有 5 条只断言 `_degraded` 的内容，那部分靠构造数据就能过；真正钉住"降级有没有发生"
的只有那两条。

## D50 插件加载结果依赖"别人有没有先调 scan()"（比 D49 严重）

**发现方式**：修 D49 时，降级日志里冒出一句 `ERROR 插件不存在: watchfiles`。
但**我手写 `scan()` 之后 `load("watchfiles")` 明明是成功的** ——
两个结论互相矛盾，于是追下去。

**这是本轮最值得写的一条**：它不报错、不缺功能、App 里跑起来一切正常。

### 根因：单例的"初始化责任"没有归属

```python
# core/app.py:152-153   ← 只有这里代劳
self.plugin_loader = get_plugin_loader()
plugins = self.plugin_loader.scan()

# services/file_service.py:26 / voice_service.py:26 / ai_service.py:24
self.plugin_loader = get_plugin_loader()   # ← 只拿单例，不扫盘
```

三个 Service **默认"别人已经扫过了"**。于是同一个 `FileService()` 有两副面孔：

| 构造时机 | `loader.plugins` | `file_monitor` 实际类型 |
|---------|-----------------|----------------------|
| 在 `App` 之后（App 扫过盘） | 9 个 | `WatchfilesMonitor` ✅ |
| 独立构造 / 在 App 之前 | **0 个** | `NullFileMonitor` ❌ |

**受控 A/B 实测**（`tools/audit_d50_order.py`，同一个类、只改顺序）：

```
甲. 先 scan() 再构造：单例 plugins 键数 = 9  → file_monitor = WatchfilesMonitor
乙. 重置成"从未 scan"：单例 plugins 键数 = 0  → file_monitor = NullFileMonitor
```

### 为什么"报错消息本身"也是缺陷

```
[ERROR] 插件不存在: watchfiles
```

**这句话是错的。** 真相是"**这个 loader 还没发现任何插件**"。
两种完全不同的故障（真没有 / 没扫盘）在日志里长得一模一样，
读日志的人会被引向"去查插件目录"，而问题在调用顺序。

### 修复

1. **懒扫盘**：`load()` 在 `plugins` 里找不到时，若从未扫过盘就先 `self.scan()`。
   新增 `self._scanned` 标志（**不用 `if not self.plugins`** ——
   "扫过了但一个插件都没有"是合法状态，那种情况下不该每次 load 都重扫磁盘）。
2. **报错自证**：消息改成
   `插件不存在: X（扫描目录 plugins，已发现 9 个: [...]）` ——
   空列表就是"没扫盘"，一眼可辨。

**实测（改前 → 改后）**：独立构造 `FileService()`
`file_monitor` 由 `NullFileMonitor` → **`WatchfilesMonitor`**。

### 反方向验证

拆掉懒扫盘 + 报错自证 → **5 failed / 5**，且**拆后的文件 `py_compile` 通过**
（说明红的是断言失败，不是导入错误）。

> ⚠️ **第一次拆的时候我拆坏了**：只删了 `if` 的执行体，留下空 `if` →
> `IndentationError` → pytest **收集期**报错。那**不能**算"用例变红"，
> 证明力弱得多（任何语法错误都会让它红）。改成整段替换后才是有意义的验证。

> ⚠️ **还有一次假绿**：我用 `python -c` 做字符串替换，PowerShell 把多行字符串里的
> 引号吃掉了，脚本 `SyntaxError` 退出 —— 而 pytest 紧接着打的是
> **「5 passed」**。差一点就记下"反方向验证通过"。
> 判据：**替换脚本自己必须断言"文件确实变了"**（`assert s != before`），
> 否则"没改成"与"改对了"在输出上无法区分。这条已写进 `tools/_d50_reverse.py`。

### 留下的判据（D49 + D50 共用）

14. **"没加载"不等于 `None`** —— 本项目凡是用空对象
    （`NullEmbedding` / `NullVectorDB` / `NullFileMonitor` …）做降级的地方，
    `x is None` **一律接不住**。空对象有自己的契约：`is_available()` 返回 `False`。
    检查方法：`git grep -n 'is None'` 逐处核对它判的是不是空对象；
15. **配置里的引擎名必须能在 `scan()` 输出里找到** ——
    判据不是"目录存在"，而是"目录里有 `plugin.py`"。
    0 字节的 `__init__.py` 让目录**看起来**像插件包（`git grep` 找目录名会命中），
    `scan()` 却看不见它，两边不一致；
16. **报错要能追到"哪一行配置"或"我确实找过"** ——
    「插件不存在: X」与「查询向量化失败」都是**没有归因**的日志：
    说的是症状，不是原因。判据：**用户看到的那条错误里，
    能不能读出该改哪个配置键 / 该换哪条调用路径**；
17. **单例的初始化责任必须有归属** ——
    凡是"别人调过我才对"的初始化，早晚会在某个入口上失效，
    而且**失效时是静默降级**（拿到空对象，功能消失但不报错）。
    判据：**同一个类的两次构造，结果不该取决于谁先跑**。
